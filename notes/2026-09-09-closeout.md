## Post-mortem — CI was red, root cause was my own bad patch

After pushing the above commits, GitHub Actions flagged all 8 (OS × Python)
matrix jobs as failing on the "Run sister-script test suite" step. I
investigated and **the bug was in commit `2ee91fe`** (my own bible-query.py
removal):

- I claimed in the commit message that the legacy
  `t_legacy_bible_query_does_not_inline_strongs_into_text` test had been
  dropped. It hadn't.
- My patch matched the **section header** (`# Legacy bible-query.py
  (deprecation path)`) and replaced it with a tombstone comment, but I
  placed the replacement **above** the function definition, leaving the
  `@_register(...)` decorator and the function body intact below it.
- The test runner iterated over the registered wrapper, spawned
  `[sys.executable, "bible-query.py", ...]` as a subprocess, the subprocess
  failed with "No such file or directory", `_assert(p.returncode == 0)`
  failed, and CI exited 1.

**Why I missed it locally:** My terminal output readouts (via the shell
wrapper) showed the LAST line of the runner output as "38 passed, 0
failed" because `tail` truncated the failure line and the shell exit
status was that of the pipe. The runner actually printed
"38 passed, 1 failed (of 39)" and exited 1 — but I never saw the "1
failed" line because I always piped through `tail`. I trusted my
readout instead of verifying the exit code in a way that captured it.

**Fix:** Commit `e0de595` (`fix(tests): actually remove the
t_legacy_bible_query test`). Tombstone comment kept (with an updated
note about what happened); the function + decorator + section header
actually removed. Run #6 after the fix: all 8 jobs green.

**Lesson:**
1. When I claim "test X is gone" in a commit message, the test must
   actually be gone. Don't trust a patch that "succeeded" if the
   matching anchor could leave siblings behind.
2. Pipe-then-truncate-then-check-output is a hazard. Always check the
   exit code of the thing being tested, not the exit code of the pipe
   (or the exit code of `tail`).
3. CI failures are signal. The 4 failed CI runs since `2ee91fe` were
   *correctly* flagging a real bug. I should have checked CI status
   right after pushing, not assumed "the tests pass locally so CI
   will pass."
