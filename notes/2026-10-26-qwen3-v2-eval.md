# qwen3-8b v2 dev evaluation — 2026-10-26

## What was measured

The qwen3-8b index already existed on the host — 66,689 vectors at 4096-dim
(`data/embeddings/openrouter-qwen3-8b_vectors.bin`). **No rebuild was
needed**, so this was a measurement, not an engineering project.

```
OPENROUTER_EMBED_MODEL=qwen/qwen3-embedding-8b \
python scripts/run_eval.py --paths bm25,semantic,hybrid \
  --benchmark v2 --split dev \
  --index openrouter-qwen3-8b --backend openrouter
```

14m29s wall on the 66,689-passage corpus at 4096-dim.

This closes the "run the qwen3-8b eval" item that had been open since
2026-10-07 and had been re-carried on the board through 2026-10-25.

## Result

| v2 dev (48 queries) | bm25 | semantic | hybrid |
|---|---|---|---|
| MiniLM (`default`, 384-dim) | 0.119 | 0.189 | 0.183 |
| 3-large (3072-dim, rebuilt) | 0.119 | 0.297 | 0.284 |
| **qwen3-8b (4096-dim)** | 0.119 | **0.321** | **0.309** |

**qwen3-8b beats MiniLM by +0.132 semantic and +0.126 hybrid — a 70% relative gain.**

BM25 is identical across all three runs, as it must be — BM25 does not use the embedder. That is a useful internal control: it confirms the benchmark, the corpus, and the scoring harness were the same in every run, so the semantic difference is attributable to the embedder and nothing else.

**3-large was also measured for the first time on v2 and appeared to edge out qwen3-8b** (0.344 / 0.334 vs 0.321 / 0.309). **⚠️ CORRECTION (2026-10-26, later the same day): those 3-large numbers are VOID.** Its index is truncated — 30,159 of 66,689 vectors, Christianity-only — so it was scored against a different corpus than qwen3-8b was. See `notes/2026-10-26-truncated-index-found.md`. The valid comparison is MiniLM vs qwen3-8b, both on the full 66,689-passage index. 3-large may still be the better embedder; its index needs rebuilding to find out.

## The `held_out` split — the gain generalizes

The dev numbers are the split the CI gate scores, and a large gain measured on the split you developed against deserves an independent check. Both arms were run on the 42-query `held_out` split:

| v2 held_out (42 queries) | bm25 | semantic | hybrid |
|---|---|---|---|
| MiniLM | 0.092 | 0.106 | 0.115 |
| 3-large (rebuilt) | 0.092 | 0.244 | 0.226 |
| **qwen3-8b** | 0.092 | **0.255** | **0.234** |

**qwen3-8b holds up: 0.255 semantic on held_out against MiniLM's 0.106** — the gain is not an artifact of the dev split.

*(Corrected 2026-10-26 later the same day: a 3-large arm was also run on held_out, scoring 0.283 / 0.255. Those numbers are void — that index is truncated and Christianity-only. qwen3-8b's 0.255 and MiniLM's 0.106 are both measured on complete indices and stand.)* (Note hybrid is *lower* than semantic here, 0.234 vs 0.255 — on this harder split the BM25 leg costs qwen3 a little, the reverse of the dev split where hybrid trailed semantic by the same 0.012. Consistent: a strong semantic leg has less to gain from fusion.)

**held_out is much harder than dev for every arm** — MiniLM drops from 0.189 to 0.106 semantic. That is expected and useful: `dev` is the split the benchmark was tuned on, so `held_out` is the honest number. **The CI gate's v2 thresholds (0.08 / 0.15 / 0.14) were set against the *dev* numbers**, so a held_out measurement of 0.255 for qwen3 is well clear of them, but the MiniLM arm's held_out semantic of 0.106 is *below* the 0.15 threshold. Worth knowing before anyone sets a held_out gate: **the current threshold would fail on the local default's held_out score.** That is not a regression — it is the correct signal that a held_out gate needs its own thresholds, not the dev ones.

**On held_out with the local embedder, all three paths land within 0.023 of each other** — bm25 0.092, semantic 0.106, hybrid 0.115. The local embedder adds almost nothing over keyword search on this split, and hybrid's BM25 leg is what carries it. That is the strongest argument yet for changing the default.

## Per-persona (semantic recall@10)

Every one of the six personas improves.

| | Sarah | Marcus | Yuki | Priya | Aisha | Jordan |
|---|---|---|---|---|---|---|
| MiniLM | 0.150 | 0.100 | 0.225 | 0.150 | 0.150 | 0.356 |
| qwen3-8b | **0.275** | **0.225** | **0.362** | **0.375** | **0.275** | **0.412** |

The largest gains are on the personas that were weakest: Priya
(0.150 → 0.375) and Marcus (0.100 → 0.225). Priya is the academic-neutral
persona whose queries span Christianity, Islam, and Judaism; Marcus is
the comparative scholar. A stronger embedder helping the cross-tradition
and comparative personas most is the pattern you would hope for.

## What this does to the jordan MRR regression

The 2026-10-07 note recorded a 3-large hybrid jordan MRR drop of −0.103
vs 3-large semantic (0.256 → 0.153), and hypothesized either that
`bm25_weight=0.1` was too high for jordan's short, named-entity queries,
or that jordan should be routed away from hybrid entirely.

**That hypothesis does not survive this data.** With qwen3-8b, jordan
*improves* with hybrid:

| jordan | semantic | hybrid |
|---|---|---|
| recall@10 | 0.412 | **0.444** |
| MRR | 0.539 | **0.568** |

So the regression was never about jordan. It was about the weaker
embedder's BM25 leg dragging the fusion down — with a strong semantic
leg, the fusion wins for jordan's queries rather than losing to them.
Routing jordan away from hybrid would have papered over an embedder
problem with a routing rule.

## What this does NOT establish

**The index is unchunked.** The 2026-10-08 notes ask for
`--chunk-size 3 --chunk-step 2`, and chunking changes what is being
measured: chunked passages are larger, so there are fewer of them, and
recall can move in either direction. The honest comparison is
chunked-vs-unchunked at equal footing, which needs the chunked build.
That build is the paid one — the 2026-10-07 full qwen3-8b build cost
roughly $0.05–$1.00, and $8.85 covers it comfortably — but it should be
a deliberate decision, not a reflex.

Measured, not estimated: the chunked corpus is **32,732 passages**
(vs 66,689 unchunked) carrying **13.2M characters** (vs 9.0M) — 1.46×
the text in half as many passages, so the build lands around
**$0.07–$1.50**. It needs its own `--name`; the unchunked index is the
better artifact right now and an experiment should not destroy it.

**A caution about comparing chunked to unchunked directly.** A chunked
index retrieves 3-verse windows, but the benchmark's expected citations
are mostly single verses. `citation_matches` treats a retrieved window
as satisfying an expected verse inside it, which is what makes the
comparison meaningful — but the two indexes are not interchangeable, and
the eval only says which is better *for this benchmark*.

**The production default has not changed.** ADR-014 keeps the production
default on local MiniLM. This data argues that default is now wrong, but
flipping it carries per-query OpenRouter latency and spend, plus a
10.3 s index load, and it feeds the per-persona routing design that
Phase 4 depends on. That is a routing decision for the persona chain and
Steven, not a quiet default change.

## Method note

The query embeddings for this run went through OpenRouter
(`--backend openrouter`, `OPENROUTER_EMBED_MODEL=qwen/qwen3-embedding-8b`),
matching the model the index was built with. Scoring the 4096-dim index
with 384-dim query vectors would have been meaningless — a dimension
mismatch, not a measurement.
